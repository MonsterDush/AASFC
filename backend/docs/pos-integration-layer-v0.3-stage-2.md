# POS Integration Layer v0.3: этап 2

Второй этап подключает действующий импорт QuickResto к каноническому контуру Raw → ACDM → ReportFacts
в режиме теневой записи. Существующая помесячная очередь остаётся единственным исполнителем импорта,
а `DailyReport`, Finance, Payroll и Analytics продолжают читать текущий путь.

## Очередь и диапазоны

`QuickRestoImportBatch` связан один-к-одному с `IntegrationImportBatch` и одним `IntegrationSyncJob`, но
не дублируется новой очередью. Канонический batch заранее содержит `IntegrationImportChunk` для каждого
календарного месячного полуинтервала. Один пользовательский запуск по-прежнему создаёт диапазон
`[period_start, period_end_exclusive)`. Текущие правила сохраняются: двухдневное перекрытие, локальная
фильтрация по `business_date`, восстановление зависшего worker, сохранение успешных месяцев и повтор
точно с упавшего chunk. Попытки, run, ошибка, counters и provenance каждого chunk хранятся отдельно.

Каждый `QuickRestoSyncRun` связан с одним `IntegrationSyncRun`. Канонический cursor подтверждается только
после завершения теневой записи. Статусы управляющего контура: `PENDING`, `RUNNING`, `SUCCEEDED`,
`FAILED`, `PARTIAL`, `CANCELLED`.

## Адаптер и возможности

`QuickRestoProviderAdapter` оборачивает текущий read-only клиент. Авторизация, retry, rate limit,
пагинация и fallback серверных фильтров остаются внутри провайдерного слоя. Состояние `SUPPORTED`
фиксируется только после реального успешного запроса. Возможности, получаемые из OrderInfo, отмечаются
как `DERIVED`; сотрудники, посещаемость и неподтверждённые складские операции не заполняются вымышленными
данными.

Если QuickResto отклоняет или игнорирует серверный фильтр, клиент выполняет локальное ограничение по
времени закрытия, затем по `business_date`. Диагностика содержит причину, режим и количества строк без
credentials и payload.

## Raw, ACDM и сопоставления

Зашифрованный allowlisted shift bundle сохраняется в `IntegrationRawObject` до нормализации. Разные
`source_version` или payload hash сохраняются отдельными версиями для replay; точный повтор остаётся
идемпотентным. Downgrade миграции блокируется, если уже накоплено несколько версий одной внешней
сущности: оператор должен сначала экспортировать или согласовать их, поэтому откат не удаляет Raw
незаметно. После этого
идемпотентно обновляются `POSBusinessShift`, `POSOrder`, `POSOrderItem`, `POSOrderEvent`, `POSPayment`,
`POSRefund` и `POSOrderDiscount`, а также доступные справочники заведений, касс, складов, типов оплат,
групп и товаров. Внешняя идентичность всегда ограничена `connection_id`.

`business_date` и `shift_slot` вычисляются общей версионированной `VenueReportingPolicy`; QuickResto
передаёт ей локальное время начала смены и не содержит собственной формулы календарной группировки.

Текущие QuickResto-сопоставления зеркалируются в канонические таблицы типов оплат, групп и департаментов,
распределений и KPI-товаров. Неподтверждённые сущности остаются `UNMAPPED`; неизвестные ссылки и ошибки
нормализации попадают в `IntegrationQuarantine` вместе со ссылкой на raw и sync run.

`POSEmployeeMapping` хранит `pos_employee_id`, `venue_member_id`, тип и confidence сопоставления, а также
явное подтверждение пользователем. Неподтверждённое предложение по ФИО не может записать
`venue_member_id`; у QuickResto эта capability пока отмечена как `UNAVAILABLE`.

## Теневая проекция и происхождение

Для каждого `business_date` и `shift_slot` формируется `POSReportProjection`. Она сравнивает количество
документов, смены, заказы, возвраты, выручку, оплаты, списания, скидки, департаменты, KPI, нераспределённую
выручку, дату, слот и статус отчёта с текущей QuickResto-проекцией. Расхождение хранится в
`IntegrationReconciliationRun` и содержит ссылки на raw и канонические документы. Нарушение финансовых
инвариантов создаёт quarantine issue и блокирует обновление ранее подтверждённой проекции.

`ReportValueContribution` хранит POS-вклады выручки, оплат, департаментов, KPI, нераспределённой выручки,
возвратов, скидок и списаний со ссылкой на проекцию и её canonical coverage. Повторная синхронизация
заменяет только записи `source_type=POS`; `MANUAL` и `ADJUSTMENT` не удаляются. На втором этапе эти записи
не заменяют `DailyReportValue`: они предназначены для проверки и будущего явного переключения источника.

## Feature flags и совместимость

Канонический управляющий контур активируется только для провайдера из
`POS_INTEGRATION_PROVIDER_ROLLOUT`. Запись Raw/ACDM дополнительно требует
`POS_INTEGRATION_SHADOW_WRITE_ENABLED`. `POS_INTEGRATION_CANONICAL_READ_ENABLED` на втором этапе не
включается, а `read_mode` принудительно остаётся `LEGACY`.

Ручное заполнение отчётов сохраняется. Активная POS-интеграция не выбирает источник автоматически,
не подменяет устаревшие данные ручными и не изменяет вручную введённые значения через теневую проекцию.

## API и выходной гейт

История помесячного импорта показывает canonical batch/job/run, fallback, количество совпавших и
проблемных ACDM-групп. Из истории можно открыть legacy-проблему, quarantine-запись или reconciliation.
Read-only API качества расположен под `/pos-integrations/{connection_id}`.

Этап считается готовым к третьему только после идемпотентного повторного импорта представительных
диапазонов, точного повтора упавшего месяца, совпадения shadow compare и воспроизводимости каждой суммы
до raw. Необъяснённые расхождения остаются блокером переключения чтения.
