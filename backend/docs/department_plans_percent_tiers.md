# Планы департаментов и пороги процента

## Пользовательский сценарий

Страница `/owner-department-plans.html` разделяет два независимых источника:

- план департамента на месяц;
- планы департамента по конкретным датам.

В дневном режиме владелец задаёт значения для понедельника–воскресенья и применяет их к неделе, месяцу или произвольному диапазону. После массового заполнения каждую дату можно изменить отдельно. Пустое значение означает, что план не установлен; ноль не используется как скрытый порог.

Факт и выполнение рассчитываются только по отчётам со статусом `CLOSED`. Дневные и ночные отчёты одной даты суммируются. День с закрытым отчётом и нулевой выручкой возвращает факт `0`, а день без закрытого отчёта — `null`.

## API планов

- `GET /venues/{venue_id}/department-plans/{department_id}/calendar?month=YYYY-MM` — месячный план, факт и календарь дат;
- `PUT /venues/{venue_id}/department-plans/{department_id}/month?month=YYYY-MM` — установить или удалить месячный план;
- `PUT /venues/{venue_id}/department-plans/{department_id}/day?date=YYYY-MM-DD` — установить или удалить план даты;
- `PUT /venues/{venue_id}/department-plans/days/bulk` — разложить значения дней недели по диапазону.

Для массовой перезаписи клиент сначала отправляет `dry_run=true`. Если будут заменены существующие значения, backend возвращает количество дат и `preview_token`. Повторный запрос с этим токеном применяет только тот набор изменений, который пользователь подтвердил. Изменившийся после предпросмотра набор требует нового подтверждения.

Чтение факта использует финансовые права существующего economics-контракта. Запись требует активного участника заведения и `PAY_PROFILES_MANAGE` (владелец и администратор проходят существующие проверки ролей).

## Ступени процента

Базовый процент остаётся в `PayComponent.percent_bps`. Дополнительные ступени хранятся в `pay_component_percent_tiers` и принадлежат одному компоненту:

- `threshold_value` — процент выполнения плана либо абсолютное значение KPI;
- `percent_bps` — ставка в basis points;
- `sort_order` — порядок для стабильного отображения.

Пороговые источники остаются в родительском компоненте: план заведения или департамента за месяц/день и KPI-метрика. Одинаковые пороги, отрицательные значения и снижение ставки на следующей ступени отклоняются. UI ограничивает редактор десятью ступенями.

`REPLACE_ALL` применяет ставку максимальной достигнутой ступени ко всей базе. `EXCESS_ONLY` считает каждый участок между порогами своей ставкой и разрешён только когда база начисления совпадает с базой плана. Старое несовместимое правило при чтении рассчитывается как `REPLACE_ALL` и записывает причину fallback в snapshot; создать новую несовместимую конфигурацию API не позволяет.

Для дневного источника каждая дата оценивается независимо. Если план даты отсутствует, в этот день применяется базовая ставка. Для месячного источника ступень определяется один раз по итогам месяца. KPI использует абсолютные значения порогов.

## Совместимость и история

Миграция `d3e5f7a9b1c2` создаёт одну эквивалентную ступень для каждого действующего legacy boost. Старые поля не удаляются, поэтому старые клиенты и rollback приложения продолжают читать компонент. Новые формы передают `percent_tiers`; расчёт в первую очередь использует дочерние строки.

При расчёте payroll в `PayrollLine.breakdown_json` сохраняются источник, департамент или KPI, план, факт, выполнение, все настроенные ступени, достигнутая ступень, применённая ставка, режим, дневные строки и итоговая сумма. Экран расшифровки читает этот сохранённый snapshot. Последующее изменение профиля или плана не меняет уже рассчитанный payroll run; новый результат появляется только после явного перерасчёта периода.

Одношаговый downgrade удаляет таблицу ступеней, но не трогает сохранённые payroll snapshots и legacy поля. После rollback многоступенчатые настройки недоступны до повторного upgrade.
