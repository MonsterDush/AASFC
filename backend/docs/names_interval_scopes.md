# Локальные имена и несколько должностей у интервала

Изменения от `develop` (`37e1ef641e486c09dee836e889fc93ca59c4cb42`), ветка
`codex/complete-names-intervals`.

## Поведение

- API графика, комментариев, доступности, обменов, сотрудников и зарплат
  использует локальную подпись `VenueMember.owner_note` в `display_name`.
  Менеджер получает такое же отображаемое имя, как владелец. Право изменять
  подпись и видимость отдельного поля `owner_note` сохраняются.
- Глобальный профиль `User` не изменяется. При отсутствии локальной подписи
  имя выбирает существующий backend helper.
- В трёх редакторах интервала (отдельная страница, мастер настройки,
  создание из графика) можно выбрать несколько должностей. Пустой список
  означает «Все должности».
- При создании смены можно сначала выбрать сотрудника. Интервалы фильтруются
  по всем его активным должностям; затем выбирается конкретная должность
  для начисления зарплаты. Можно по-прежнему создать смену без сотрудника.
- Проверка новых назначений сравнивает ID должностей из каталога,
  поэтому переименование не разрывает связь с интервалом.

## Граница изменений для существующих смен

По запросу владельца проекта существующие назначения не перепроверяются
при изменении интервала смены или списка разрешённых должностей интервала.
Их сотрудник и `venue_position_id` сохраняются. Миграция не изменяет таблицы
`shifts` и `shift_assignments`.

Логика обменов, восстановления назначенных смен и применения шаблонов
сохранена. Текущие шаблоны создают пустые смены и не содержат назначения
конкретного сотрудника. Ограничение применяется при последующем ручном
назначении; при восстановлении прежнее назначение сохраняется.

Планы департаментов и процентные ступени в этот пакет не входят.

## Контракт API

- `POST/PATCH /venues/{venue_id}/shift-intervals[/…]` принимает
  `position_ids: [catalog_position_id, ...]`. `[]` снимает ограничение;
  отсутствие поля в PATCH сохраняет его.
- Старый `position_id` принимается как одиночный выбор. Конфликтующие
  `position_id` и `position_ids` возвращают 422. Ответ содержит оба поля;
  `position_id` показывает первый выбранный ID для старых клиентов.
- Интервалы возвращают `position_ids` и `position_titles`, должности
  сотрудников — `catalog_position_id`.
- `POST /venues/{venue_id}/shifts` дополнительно принимает необязательный
  `venue_position_id`. Смена и назначение сохраняются одной транзакцией.
- Несовместимое новое назначение возвращает 409 с
  `detail.code = SHIFT_INTERVAL_POSITION_MISMATCH` и текстом в `detail.message`.
- Используются существующие permission codes, новые права не добавляются.

## Миграция и откат

Миграция `c2f4a6b8d0e1` после `b9d2e4f6a8c1` добавляет
`venue_positions.catalog_position_id` и `shift_interval_positions`.
Назначенные должности связываются с существующим каталогом своего заведения.
Старые ограничения переносятся с сохранением прежнего сопоставления
названий без учёта регистра и внешних пробелов. Поэтому старое ограничение
может включить несколько одноимённых записей каталога.

Порядок применения: `alembic upgrade head`, запуск обновлённого backend,
обновление frontend. Версии изменённых JS-модулей в HTML/import обновлены;
английский каталог загружается существующим `fetch(..., {cache: "no-cache"})`.

Откат к `b9d2e4f6a8c1` разрешён, если у каждого интервала не более одной
должности. Если есть несколько, миграция останавливает откат до изменения
схемы: сначала нужно явно выбрать одну должность либо «Все должности» через
новый интерфейс. Многозначные настройки не отбрасываются автоматически.
