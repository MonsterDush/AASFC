# POS Integration Layer v0.3 — этап 3

## Результат

Этап добавляет provider-neutral контур для данных, которые не должны быть привязаны к схеме QuickResto или iiko:

- рецептуры и ингредиенты;
- склады, снимки остатков и движения;
- поставщики, закупки и строки закупок;
- списания и строки списаний;
- инвентаризации и строки инвентаризаций;
- фактическая посещаемость сотрудников;
- единые проверки качества и оценку свежести capability;
- каноническое представление составных позиций заказа.

Денежные поля хранятся как `Numeric(20, 4)`, количества — как `Numeric(20, 6)`. Каждая внешняя сущность имеет уникальную пару `(connection_id, external_id)`, provenance-поля, soft-delete и ссылку на integration connection.

## Capability-first правило

Наличие канонической таблицы не означает, что конкретный провайдер умеет её заполнять. Capability получает `SUPPORTED` только после успешного реального probe. `DERIVED` допустим, когда источник проверен, а сущность однозначно выводится из него.

Для QuickResto склады выводятся из проверенного `stores` endpoint. Рецептуры, остатки, движения, поставщики, закупки, документы списаний, инвентаризации и attendance остаются `UNAVAILABLE`, пока для них не подтверждён read-only источник. Сумма списаний, вычисленная из заказов, не считается документом складского списания.

## Составные блюда

QuickResto и iiko payload нормализуются в одинаковую структуру:

- родитель получает роль `COMPOUND` и хранит финансовую сумму;
- дочерние строки получают `COMPONENT` или `MODIFIER`, роль компонента и ссылку на родителя;
- дочерние строки с `included_in_parent=true` не добавляют сумму второй раз;
- исходный payload продолжает храниться в raw-слое для replay и повторной нормализации.

Golden fixtures проверяют одинаковую каноническую форму для эквивалентных составных блюд QuickResto и iiko.

## Качество и эксплуатация

Общий валидатор формирует стабильные коды для отрицательной выручки, закрытого заказа без оплаты, неизвестного сотрудника/товара, заказа без позиций, закупки без поставщика и неизвестного товара инвентаризации. Эти коды предназначены для существующего `integration_quarantine` и retry-контура.

`GET /pos-integrations/{connection_id}/quality-summary` возвращает:

- общий health (`HEALTHY`, `DEGRADED`, `FAILED`);
- число активных и критических quarantine issues;
- число устаревших или ещё не полученных capabilities;
- freshness каждой capability относительно переданного порога.

## Безопасное включение

1. Применить миграцию `f8c2d4e6a1b3`.
2. Оставить неподтверждённые capabilities выключенными.
3. Для нового provider endpoint сохранить raw payload и прогнать normalizer/golden tests.
4. Выполнить bounded shadow replay и сверку финансовых инвариантов.
5. Включать canonical read отдельно для каждого заведения только после `MATCHED` reconciliation.
6. Сохранять legacy/manual contributions как rollback path; физическое удаление старых таблиц не входит в этот этап.

## Внешний gate для iiko

Код обрабатывает compound-item DTO и готов к подключению P1/P2-сущностей, но реальные iiko capabilities нельзя объявлять `SUPPORTED` без credentials, организации и успешных probe вызовов конкретного API. Подключение endpoint, mapping и production rollout выполняется capability за capability по правилам выше.
