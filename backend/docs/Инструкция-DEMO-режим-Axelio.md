# Инструкция по взаимодействию с DEMO-режимом Axelio

## Назначение
DEMO-режим нужен для того, чтобы пользователь с лендинга мог посмотреть Axelio на живых заранее подготовленных данных, не имея возможности что-либо изменить.

---

## Как пользователь попадает в DEMO
1. На лендинге нажимает кнопку **«Попробовать»**.
2. Backend создаёт DEMO-сессию и авторизует пользователя в специальном режиме.
3. Пользователь попадает внутрь приложения в **read-only DEMO**.

---

## Что пользователь видит в DEMO
Пользователь видит:
- реальные страницы приложения;
- заранее заполненные данные;
- DEMO-месяц с подготовленным сценарием;
- глобальную компактную DEMO-панель над хэдером.

DEMO не должен выглядеть как набор моков или пустых экранов.

---

## DEMO-панель
DEMO-панель должна присутствовать **на каждой странице**, открытой в DEMO.

### Требования к панели
- располагается **над основным хэдером**;
- занимает **одну строку**;
- остаётся читаемой;
- не должна сильно съедать вертикальное пространство;
- на узких экранах допускается горизонтальный скролл внутри панели.

### Состав панели
Панель содержит:
- метку **«Пробный режим Axelio»**;
- переключатель режима просмотра:
  - **Владелец**
  - **Персонал**
- подпись с DEMO-периодом, например: **«Данные: март 2026»**;
- кнопку **«На сайт»**;
- кнопку **«Оставить заявку»**;
- кнопку **«Начать пользоваться»**.

---

## Переключение между режимами
В DEMO пользователь может переключаться между двумя режимами просмотра:

### 1. Владелец
Показывает DEMO как для владельца заведения:
- карточка заведения;
- сводка;
- расходы;
- зарплаты;
- справочники;
- прочие owner-экраны.

### 2. Персонал
Показывает DEMO как для сотрудника:
- график;
- мои смены;
- зарплата;
- доступные staff-экраны.

### Важно
Это не просто визуальное скрытие кнопок.
Переключение должно менять **контекст DEMO-сессии**, чтобы backend и frontend одинаково понимали, какая persona сейчас активна.

---

## Что можно делать в DEMO
Пользователь может:
- переходить по страницам;
- смотреть данные;
- переключать режим Владелец / Персонал;
- открывать карточки, сводки, графики, начисления;
- возвращаться на сайт;
- нажимать CTA-кнопки.

---

## Что нельзя делать в DEMO
Пользователь **не должен иметь возможности изменить данные**.

Запрещаются любые действия, которые меняют состояние системы:
- создание;
- редактирование;
- удаление;
- сохранение;
- архивирование;
- закрытие/переоткрытие отчётов;
- приглашения участников;
- редактирование настроек;
- изменение профиля;
- любые прочие mutation-действия.

---

## Как должна работать блокировка изменений
Блокировка должна быть двойной:

### 1. На backend
Backend является источником истины.
Если запрос в DEMO пытается изменить данные:
- backend возвращает `403`;
- код ошибки: `DEMO_READONLY`;
- текст: **«Это пробный режим. Изменения здесь недоступны.»**

### 2. На frontend
Frontend заранее скрывает или дизейблит явные mutation-кнопки там, где это уместно.

Если пользователь всё же дошёл до запрещённого действия:
- показывается понятный toast:
  - **«Это пробный режим Axelio. Здесь можно изучить интерфейс, но изменения недоступны.»**

---

## DEMO-данные
DEMO должен быть заполнен заранее и не зависеть от текущего календарного месяца.

### Основной принцип
Используется **фиксированный DEMO-период**, например:
- март 2026.

### Что должно быть заполнено
Минимум:
- demo venue;
- demo owner;
- demo staff;
- 6–10 demo-сотрудников;
- должности;
- интервалы смен;
- график на месяц;
- закрытые отчёты;
- расходы;
- категории расходов;
- поставщики;
- зарплатные профили и начисления;
- месячная сводка;
- несколько наглядных кейсов.

### Зачем это нужно
Пользователь должен видеть не пустую систему, а ощущение уже работающего заведения.

---

## Откуда берутся demo-сотрудники
Для DEMO **не нужны реальные аккаунты**.

Используются:
- 1 DEMO-owner persona;
- 1 DEMO-staff persona;
- дополнительные DEMO-пользователи как служебные записи в базе.

Они нужны для:
- графика;
- зарплат;
- отчётов;
- общей реалистичности данных.

---

## Как суперадмин работает с DEMO
Суперадмин должен иметь возможность:
- открыть DEMO-заведение в обычном полном доступе;
- редактировать DEMO-данные;
- пересобирать DEMO;
- сбрасывать DEMO к эталонному состоянию;
- экспортировать fixture DEMO.

---

## Bootstrap / reset DEMO
### Bootstrap
Используется для автоматической сборки DEMO-данных:
- создание/поиск demo venue;
- создание DEMO-пользователей;
- заполнение месяца;
- подготовка отчётов, расходов, начислений и т.д.

### Reset
Используется для восстановления DEMO к эталонному состоянию.

### Fixture
Fixture нужен для того, чтобы:
- сохранить эталон DEMO;
- быстро восстановить его после правок;
- повторно развернуть DEMO без ручного заполнения.

---

## Как тестировать DEMO после деплоя
После деплоя нужно проверить:

### Owner flow
- вход через кнопку «Попробовать»;
- загрузка карточки заведения;
- загрузка сводки;
- расходы;
- зарплаты;
- справочники;
- отсутствие реальных mutation-действий.

### Staff flow
- переключение в режим Персонал;
- загрузка графика;
- загрузка зарплаты;
- корректность доступных staff-экранов.

### Общие проверки
- баннер есть на каждой странице;
- баннер не занимает слишком много места;
- CTA-кнопки работают;
- переключение owner/staff работает;
- DEMO не уходит в пустые месяцы без понятного объяснения;
- при попытке изменения показывается корректное уведомление.

---

## Рекомендуемый сценарий поддержки DEMO
1. Один раз собрать DEMO.
2. При необходимости руками улучшить данные через суперадмина.
3. Сохранить новый fixture.
4. При поломке или загрязнении DEMO выполнить reset.
5. Периодически проходить DEMO как пользователь и шлифовать UX.

---

## Кратко
DEMO-режим Axelio — это:
- отдельная read-only DEMO-сессия;
- глобальная компактная панель;
- переключение Владелец / Персонал;
- живые подготовленные данные;
- невозможность что-либо испортить;
- быстрый возврат на сайт и CTA на конверсию.
